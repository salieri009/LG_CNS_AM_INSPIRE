**설계는 서비스 11개와 EKS까지 갔는데, 이 저장소에서 돌아가는 코드는 아직 없음.**

내일 15시 발표에서 보는 건 "실제로 무엇이 작동하는가"임. 데모 루프 하나(A① → A② → A③ → A④ → B①)가 끝까지 도는 것만 실제로 만들고, 나머지는 Mock이라고 붙여야 함.

- 반영: D23 (실제 구현 7개, Mock 4개), 테스트 P0 24개 → 15개, EKS 시간 게이트 (11-10 12:00)

## 1. 한 문장 요약 테스트

> 독립 정비소의 신입 정비사가 처음 보는 전기차·PBV의 고장코드를 받았을 때, 어디부터 점검하고 어떻게 분해할지 몰라 작업 시간이 늘어나는 문제를, 제조사 공식 진단 순서와 같은 사양의 관측 원인 비율, 3D 분해 경로로 풀고, 그 정비 결과를 제조사의 설계 지표로 돌려줌.

- 한 문장으로 써짐
- 문제는 팀이 쓰는 한 문장이 셋이었다는 것. 기획서 맨 위는 Stack Overflow식 설명서 문단(옛 버전), README는 "공장은 조립하기 쉬운 차를 만들지만" 훅 문장, 발표 표지는 서비스 이름
- 질문: "팀원 아무나 붙잡고 물어도 이 문장이 똑같이 나오는가?"
- 반영: 기획서 한 줄 요약과 README를 이 문장으로 맞춤

## 2. Project Design Framework 8항목

| 영역 | 항목 | 판정 | 이유 | 멘토가 던질 질문 |
| --- | --- | --- | --- | --- |
| A | 01 Problem | 보완 | 출발점은 현직 정비사 지인 1명의 경험. 숫자 근거는 사전공개 논문(58.0% → 68.8%)과 재인용(약 15%)뿐 | 같은 문제를 겪는 정비사를 몇 명에게 확인했나? 한 건에 몇 분을 잃나? |
| A | 02 Target | 보완 | 메인인 신입 정비사는 분명함. 공장 담당자용 대시보드가 같이 붙어 제품이 둘로 보임 | 공장 담당자가 대시보드를 안 봐도 정비사 쪽 가치는 그대로인가? |
| A | 03 Solution | 통과 | 차종·연식·계통을 직접 골라 찾는 매뉴얼 대비, VIN 기준 점검 순서와 3D 경로라는 차이가 분명함 | 2D 단계 이미지로는 안 되는 이유는? 3D가 꼭 필요한가? |
| A | 04 Expected Impact | 위험 | 지표 정의는 있지만 측정한 숫자가 하나도 없음 | 부품 찾는 시간이 줄었다는 걸 오늘 팀 안에서 한 번이라도 재봤나? |
| B | 05 Core Features | 위험 | A①\~⑤, B①\~④, 팁 추천·배지·신고, 공유 링크까지 9개 이상. MVP 순서는 있는데 구현 계획(서비스 11개)이 그걸 따르지 않음 | 내일 15시에 화면 하나만 돈다면 어느 화면인가? |
| B | 06 UX/UI | 보완 | 기획서·저장소에는 스토리보드 표만 있고 화면 목업이 없음. "작업 중 한 손 조작" 전제와 VIN 17자리 입력이 부딪힘 | 장갑 낀 손으로 VIN 17자리를 치나? 스캔은? |
| B | 07 Service Loop | 보완 | 진단 피드백·제조 피드백 루프 설계는 명확함. 루프를 돌리는 A④ 기록을 남길 동기(보상)가 미정 | 정비사가 기록을 안 남기면 루프는 멈춤. 왜 남기나? |
| C | 08 Technical Design | 위험 | C4 L1\~L4, API 7개, 테이블 14개, EKS 탄력 설계까지 깊음. 남은 시간과 구현 범위가 안 맞음 | 서비스 11개 중 내일 실제 코드가 도는 건 몇 개인가? |

## 4. 범위 칼질

| 구분 | 항목 | 이유 |
| --- | --- | --- |
| 남길 것 1 | A② 점검 우선순위 (공식 순서 + 관측 비율·n) | 문제의 첫 장면 "어디부터 보나"에 답함 |
| 남길 것 2 | A③ 3D 분해 경로 + 고전압 잠금 | 솔루션의 차별점이고, 안전 규칙이 실제로 작동하는 걸 보여줌 |
| 남길 것 3 | A④ 결과 기록 → A②·B① 갱신 | 루프와 팩토리 연결을 보여주는 유일한 장면 |
| 뺄 것 | A⑤ 신입 모드, B③ 조기 신호, B④ 개선 제안, 팁 작성·추천·배지·신고, 고객 공유 링크 | 데모 루프 밖. 발표에서 확장 방향으로만 언급 |
| 뺄 것 | HPA·KEDA·Spot 튜닝 | 동시 사용자가 몇 명인 시연에서는 보여줄 수 없음. 설계로만 설명 |
| Mock | VIN 조회·생산 이력(production, manufacturer-mock), 로그인(auth), 단계 팁(knowledge), 과거 정비 기록 300건, B② 사양 비교 데이터 | 같은 API 모양의 고정 응답이면 데모 흐름은 그대로 |

**INPUT → PROCESS → OUTPUT**: VIN·고장코드 입력 → 공식 진단 순서 + 같은 사양 완료 기록 집계로 후보 정렬, 고른 부품의 3D 분해 단계 구성 → 점검 순서와 3D 경로 확인, 기록 제출 뒤 관측 비율과 공장 지표가 바뀐 것 확인

## 5. 의사결정 기록 점검

- "처음 생각 → 확인한 내용 → 바뀐 판단" 형식의 로그가 D1\~D22까지 있음. 가이드 형식 그대로임
- 발표에 넣을 결정 2개
  1. **D19**: LLM으로 메모 구조화·개선 제안 → 팀 시나리오에 AI가 없고 정비·안전 정보는 근거 추적이 필요함 → AI 전면 제외, 통계·규칙 기반
  2. **D17**: 질문 게시판 → 정비사는 작업 중이라 글을 쓸 여유가 없음 → 3D 단계 툴팁의 팁이 답변 역할
- AI 활용 질문: 기획 문서와 다이어그램 상당 부분을 AI 도구로 정리했음. D16은 아직 "확인 필요"이고, D22·D23은 AI 제안을 받아 적은 결정임. **이 판단은 팀이 직접 했는가?** 발표 전에 팀이 한 번 확인하고, 아니면 로그에 표시해야 함

## 7. Q&A 8분 예상 질문 (날카로운 순서)

1. **정비사 서비스인데 왜 팩토리 도메인인가?** → 원인이 공장의 조립 효율(DFA) 최적화에 있고, A④ 기록이 B① 지표 → B④ 개선 검토로 공장의 결정을 바꾸는 경로를 데모 장면으로 답함
2. **62%는 어디서 나온 숫자인가? Mock 아닌가?** → Mock 300건이라고 먼저 밝히고 산식(분모는 원인 확인 완료 건, n 30건 미만은 참고용, 고장 발생률 아님)을 보여줌
3. **서비스 11개에 EKS까지, 2일 프로토타입에 필요했나?** → 실제 코드 7개·Mock 4개 표를 보여주고, EKS는 확장 설계이며 시간 게이트를 넘기면 k3s로 바꾼다고 답함
4. **바쁜 정비사가 왜 기록을 남기나? 처음엔 데이터가 없지 않나?** → 선택형 1분, 제출하자마자 추천이 바뀌는 걸 보여줌. 초기엔 제조사 공식 설명이 기본 툴팁. 실질 보상은 미정이라고 솔직히 말함
5. **제조사가 왜 데이터를 내주나? 3D 모델은 누가 만드나?** → 권한 등급, 공정 비공개, 익명 집계가 조건. 시연은 가상 차량 저폴리 모델이고 실서비스는 제휴가 전제
